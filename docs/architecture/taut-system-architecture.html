PYTAUT 0.2.0 · CURRENT IMPLEMENTATION MAP

taut 시스템 구조

taut는 Python 백엔드 소스에서 언어 사실을 먼저 확정하고, framework provider가 의미 사실을 보강한 뒤, capability가 충분한 규칙만 실행한다. disk cache와 resident daemon은 이 canonical pipeline의 중간 상태만 재사용하며, 불확실한 사실이나 cache 실패를 통과로 간주하지 않는다.

01

한 번의 검사에서 데이터가 이동하는 경로

CLI는 모든 단계를 조립하지만, 각 단계는 자신의 앞뒤 구현을 직접 알지 않는다.

02

패키지 의존 구조와 책임 경계

domain이 공통 언어를 제공하고, 분석·설정·정책·결과 처리가 그 위에서 독립적으로 움직인다.

03

심볼 해석은 철자 추측이 아니라 발생 위치별 상태를 만든다

이름 문자열을 맞춰 보는 대신 scope와 control flow를 따라 각 참조의 후보와 확실성을 보존한다.

04

확장은 provider와 rule pack 두 축으로 분리된다

새 framework를 이해하는 코드와 그 사실을 회사 정책으로 판정하는 코드는 서로 다른 플러그인 계약을 사용한다.

05

규칙 판정과 프로세스 종료는 별도 단계다

규칙은 네 가지 의미 판정을 만들고, 마지막 보고서 조립기가 정책 강도와 신뢰 문제를 합쳐 세 가지 종료값을 정한다.

0 · TRUSTED PASS

분석이 충분하고 활성 강제 위반이 없다.

1 · POLICY FAIL

무엇을 고쳐야 하는지 확정된 강제 위반이 있다.

2 · TRUST FAIL

설정·분석·coverage 문제로 결과를 신뢰할 수 없다.

06

반복 검사는 같은 판정 경로에서 계산만 재사용한다

disk cache는 프로세스 사이에서 분석 결과를 복원하고, daemon은 메모리 안에서 변경 영향만 다시 계산한다.

08

범용 엔진과 저장소별 정책이 만나는 지점

taut 자체에는 특정 회사나 서비스의 폴더 이름이 없고, 적용 저장소의 pyproject.toml이 현실 구조를 공통 역할에 연결한다.

현재 0.2.0이 강하게 보장하는 것

결정적 정적 분석, occurrence-aware symbol 관계, capability-gated 규칙, 분석 coverage, 인증된 cross-process cache, dependency-aware resident invalidation, 재현 가능한 text/JSON 결과다.

의도적으로 범위 밖에 둔 것

실행 중 query 수와 실제 N+1, migration 안전성, LSP/editor 연결, 별도 타입 검사, 서비스별 위반 baseline은 이 정적 엔진의 책임이 아니다.
